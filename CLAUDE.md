# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Architecture

npm workspaces monorepo (`workspaces: ["packages/*"]` in the root `package.json`, which is `"private": true` so it can never itself be published). Each package under `packages/*` publishes independently to npm under the `@ledhed2222` scope.

**Every package's default entry file is `base.js`, not `index.js`.** That's deliberate, not an oversight: each package exposes multiple presets as sibling files named after what they contain (`typescript.js`, `react.js`, `prettier.js`, `scss.js`, ...), and `base.js` follows that same naming rather than the generic Node convention. The filename is never part of the public API anyway — consumers only ever see the package name and a subpath (`@ledhed2222/eslint-config`, `@ledhed2222/eslint-config/react`), resolved through the `exports` map in each package's `package.json`.

**Each preset is a separate file so optional peer deps stay optional in practice, not just on paper.** `eslint-config/base.js` only imports `@eslint/js` and `eslint-plugin-import` (both real `dependencies`, always needed). `typescript.js`, `react.js`, and `prettier.js` each have their own top-level import of their own peer dep (`typescript-eslint`, `eslint-plugin-react`/`eslint-plugin-react-hooks`, `eslint-plugin-prettier`/`eslint-config-prettier`), and nothing else imports them. Importing `@ledhed2222/eslint-config` therefore never touches `typescript-eslint` or the React plugins — verified by installing only the base deps and importing `typescript.js` directly, which fails with a clear "Cannot find package" error. **Do not collapse these into one file with conditional logic** — that reintroduces a hard dependency on every peer for every consumer, defeating the entire point of the split. Same pattern in `stylelint-config`: `base.js` only needs `stylelint-config-standard`; `scss.js` is the only file that touches `stylelint-config-standard-scss`.

All peer deps except the linter itself (`eslint`, `stylelint`) are marked `optional: true` in `peerDependenciesMeta`, so `npm install` stays quiet for consumers who don't need a given preset. The tradeoff: there's no install-time warning if a consumer forgets a peer dep for a preset they *do* use — the only signal is a runtime import error naming the missing package when their `eslint.config.js`/`.stylelintrc` first loads. That's an accepted tradeoff, not a gap to fix; see the package READMEs for the proactive documentation side of this.

## Gotchas

- **`stylelint-config`'s `scss.js` must extend `['./base.js', 'stylelint-config-standard-scss']` in that exact order.** `stylelint-config-standard-scss` sets an `overrides` entry (via its own transitive deps) that teaches stylelint to parse `.scss` files with `postcss-scss` — that's what makes `@use`, nesting, etc. work at all. `base.js` (via plain `stylelint-config-standard`) has no `overrides` field. Because stylelint's config merge does not concatenate `overrides` arrays across `extends` entries, whichever entry supplies `overrides` last wins outright — put `base.js` first, the SCSS config last, or `.scss` files start failing with `Unknown at-rule "@use"`. This was caught by an actual `stylelint <file>` lint run, not `--print-config`, which prints a resolved config that doesn't reliably surface this — verify SCSS behavior with a real lint run against real SCSS syntax, not config inspection.
- **`stylelint`'s own stylistic/formatting rules (`block-opening-brace-newline-after`, etc.) were removed from core in v16+.** Their replacements live in `@stylistic/stylelint-plugin` under an `@stylistic/` rule prefix, and it must be registered in `plugins` before those rules can be used. There is no direct replacement for the old `declaration-block-single-line-max-declarations`; "no single-line rule blocks, even with one declaration" is enforced instead by combining `@stylistic/block-opening-brace-newline-after: always` and `@stylistic/block-closing-brace-newline-before: always`.
- **`eslint-config/base.js`'s config-file exemption needs a `**/` glob prefix**: `files: ['**/*.config.{js,mjs,cjs,ts,mts,cts}', '**/*.d.ts']`. Without the `**/` prefix, the pattern only matches files directly in whatever directory ESLint is invoked from — a config file one directory down (or ESLint run from a parent directory) silently stops being exempted from `import/no-default-export`.
- **`stylelint-config-standard-scss` already pulls in `stylelint-scss` and `postcss-scss` transitively** (via `stylelint-config-recommended-scss`). Consumers of the `/scss` entry point only need `stylelint-config-standard-scss` itself as a devDependency alongside `stylelint`.
- **Only one `package-lock.json`, at the repo root.** npm workspaces resolve everything from the root lockfile; a per-package lockfile is redundant, gets ignored by npm for workspace members, and would look wrong if it ever ended up in a published tarball (it wouldn't, since `npm publish` only ships what's in that package's own directory, and none of them have their own lockfile).
- **`npm publish --access public` needs an interactive OTP/browser step even when already `npm login`-ed.** Login and publish-time 2FA are separate; expect `npm publish` to pause and print a `npmjs.com/auth/cli/...` URL the first time in a session.
- **`htmlhint-config` can't be consumed the way the other packages are.** HTMLHint's own CLI only reads a literal `.htmlhintrc` JSON file off disk — it has no `extends`-from-npm-package resolution like ESLint/Stylelint do. Don't try to make a `.htmlhintrc` that references this package by name — it won't resolve. Instead the package ships its own `bin` (`cli.js`, exposed as `htmlhint-config-lint`) that wraps `HTMLHint.verify()` with the bundled ruleset baked in, so `htmlhint` is a real `dependency` here, not a peer like `eslint`/`stylelint` are for the other packages — the CLI genuinely needs it to run, not just the consumer. `base.js`'s plain ruleset object is still exported too, for embedding in a custom script instead of using the CLI. Also deliberately excludes any rule that assumes a full document (`doctype-first`, `title-require`, `html-lang-require`, `meta-*-require`, ...), since it needs to work against bare HTML fragments/partials, not just whole pages.
